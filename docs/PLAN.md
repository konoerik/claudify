- [ ] BDD/system-level scenario stub — extend the stub-first workflow (ADR-14) with a second, higher-grain pause for behaviors that don't decompose cleanly into one function's contract: for a new user-facing behavior or flow that spans multiple components (a Flask request/response cycle, a TUI screen transition, a multi-step CLI invocation), write and pause on a Given/When/Then scenario or plain acceptance criteria — no literal Gherkin/Cucumber tooling required — before decomposing into the functions that implement it. Function-level stubs still happen within that decomposition; the two layers compose (outside-in/ATDD), they don't compete. Rationale: function-level stubs can each look individually correct while the composed flow is still wrong (e.g. an auth check happening after a side effect) — a different failure mode than a bad signature, and one function-level review doesn't catch it. Best-fit candidates: `python-flask` and `python-tui`, where `pytest-flask`'s test client / Textual's `AppTest` already give a "pending system-level test, no body yet" artifact with no new tooling needed; `simple-web`'s Stub section already informally leans on a manual scenario checklist for exactly this reason — no clean function boundary for page behavior. Main risk: ceremony stacking — two pause-points for anything touching more than one file cuts against the exploratory-work item's goal, and shares the default-to-confirm item's "not everything decomposes into obvious slices" problem above. Pilot in one blueprint before any kit-wide rule, same as that item — see its manual-toggle hypothesis, which could apply here too
